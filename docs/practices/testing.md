# Testing

## What exists

Three kinds of automated test, from fastest to slowest, and one script for the failures that only real processes can show:

| Suite | Command | Covers | Needs |
|---|---|---|---|
| **Unit tests** | `./mvnw test -Dtest='!*IntegrationTest,!*ApplicationTests,!*Tests'` from `microservices/` | Money and security logic, with its collaborators mocked: no Spring context, no infrastructure | A JDK |
| **Integration tests** (`*IntegrationTest`, `*ApplicationTests`) | `./mvnw -pl <module> test` | Each service as the real application on **real PostgreSQL, Redis and Kafka**: HTTP in, database and events out. Every migration runs on an empty database, and Hibernate validates the entities against it | **Docker only.** [Testcontainers](https://testcontainers.com) starts the containers; nothing else needs to be running, no config server, no Eureka |
| **Everything, as CI runs it** | `./mvnw verify` from `microservices/` | Both of the above, in every module | Docker |
| **Crash and outage tests** | `python chaos/crash_and_outage_test.py` from `microservices/` | Kills a service or stops PostgreSQL, Redis or Kafka under load and checks nothing is lost, duplicated or stuck. See [the results](../reliability/crash-and-outage-tests.md) | The whole stack running, as for the hand checks below |

The integration tests share one `test-support` module, which starts each container the first time a test needs it and removes it when the JVM exits. A service's tests extend `PayfloIntegrationTest` and read the service's real settings from `config-repo` through a test-only `src/test/resources/application.yaml`, so they run on the configuration the service really uses. They stub only other *services* (vault-service from payment-service, say), never the database, Redis or Kafka: the point is what a mock can't show — a native query, a unique index, a migration, Redis's atomic claim.

## What is verified by hand

Every change to a flow is verified end to end through the gateway, against the real infrastructure:

| Area | How to verify |
|---|---|
| The whole flow at once | `python demo/demo.py` from `microservices/` ([the demo](../local-development/demo-and-dashboard.md)): on a fresh database it must end with every seeded payment in its expected state, one order for the repeated idempotency key, a `PROCESSED` refund and a settlement whose net is gross − refunds − fee − GST. Then click through the dashboard it prints |
| Authentication | Signup → login → create an API key → call an API-key endpoint; a wrong secret is `401`; 201 requests in a minute on one key is a `429` |
| The payment path | Create an order with a `customer`, tokenize a card, pay by card and by UPI; each reaches `CAPTURED` within seconds and the order `PAID`. A [test failure value](../api/mock-acquirer.md) comes back `FAILED` |
| Idempotency | `python idempotency_replay_test.py` in `microservices/load-test/` — every key must resolve to one order or payment ([replay test](../load-testing/running.md#6-replay-test-for-idempotency)) |
| Compensation | Stop vault-service and pay by card: the payment ends `FAILED` with `PAYMENT_GATEWAY_ROUTER_UNREACHABLE` |
| Events | `ORDER_CREATED`, `PAYMENT_CREATED` and `PAYMENT_STATUS_CHANGED` appear on their topics in Control Center or Kafka UI |
| Webhooks | Register `…/webhook/success` as a target and watch `webhook_event` rows reach `DELIVERED`; register a URL that fails and watch `attempts` and `next_retry_at` advance |
| Settlement | Call `POST /v1/admin/settlements/run` (the operator's [admin API](../api/admin.md)) rather than waiting for 23:00 or editing the cron, then check `settlement` and the payments' `SETTLED` status. The merchant must be `ACTIVE` and have a payout account: set a profile and `PUT /v1/merchants/me/settlement-bank`, then `POST /v1/merchants/me/kyc` (the PAN `AAAAA0000A` is the rejection test). Check that a refunded payment is paid out net of the refund, and that `GET /v1/settlements` shows the run. Verified end to end: a run settles every captured payment, records gross/fee/GST/net, and the payout simulator moves it to `PROCESSED`. |
| Admin API and audit log | With `X-Admin-Key`: suspend a merchant and see its API key refused at once (`403 MERCHANT_SUSPENDED`), reactivate it, run a settlement for it; with a merchant JWT or API key on the same paths expect `401`; read `GET /v1/admin/audit-log` and the merchant's own `GET /v1/merchants/audit-log` for the entries |
| Capture failure | Pay by UPI with `capturefail@okaxis`: the payment ends `AUTHORIZED` with `CAPTURE_DECLINED` and the order stays unpaid; `POST /v1/payments/{id}/capture` then captures it and marks the order `PAID` |
| Card testing | Decline several card payments in a row (card `4000000000000002`, enough to pass 20 failures at over half of the merchant's card payments) and see `429 CARD_TESTING_SUSPECTED` for cards while UPI still works; tokenize 31 cards in a minute and see `429 CARD_TOKENIZATION_LIMIT_EXCEEDED` |
| Webhook signing | Register a receiver, and check `X-PayFlo-Timestamp` and `X-PayFlo-Signature` with `WebhookSignatures.verify` (or the recipe in [webhook configs](../api/webhook-configs.md)); a failing receiver's retry carries a new timestamp |
| Kubernetes | The steps in [running on kind](../deployment/running-on-kind.md) — last done on a fresh cluster with `k8s-scaled` (3 gateways, 3 payment-services): all pods healthy, signup, login and API keys for 50 merchants, then about 800,000 requests of orders and payments by card, UPI and net banking through the NodePort with no errors outside the rollouts, a rolling restart of both services under load (19 failed requests in 226,834, [scaling](../deployment/scaling.md#rolling-out-under-load)), and the database checked afterwards for duplicate or stuck payments (none) |

A green build says nothing about these on its own: they are the checks across services that the integration tests, which run one service at a time, don't make. The [crash and outage tests](../reliability/crash-and-outage-tests.md) automate the failure half of them.

## Load testing

The JMeter plan in `microservices/load-test/` drives orders and payments through the gateway, reports the throughput, and grades the run's p99 latency and error rate. See [load testing](../load-testing/README.md).

## Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull request: `docs/api/check_openapi.py` (the [OpenAPI spec](../api/openapi.yaml) must name exactly the endpoints the controllers have), `./mvnw verify` (every unit and integration test, on the Docker the runner already has) and a dependency scan. The scan builds a CycloneDX bill of materials from Maven's fully resolved dependencies, publishes it as a build artifact, and has Trivy fail the build on any HIGH or CRITICAL vulnerability that has a fix; it also fails on a committed secret, and reports (without failing) HIGH and CRITICAL configuration problems in the Kubernetes manifests. The workflow passes `actionlint`, and the scan was run locally in Docker with the same scanner before the first push, which is how the dependency upgrades below were found. The pipeline runs green on GitHub.

## Adding tests

- Business logic — the state machine table, fee and GST arithmetic, the saga's compensation, the mock processors — suits plain JUnit tests that construct the class directly and mock its collaborators, with no Spring context and no infrastructure.
- A controller change suits a `@WebMvcTest` slice with the service mocked; `MerchantContext` can be populated by sending `X-Merchant-Id`.
- A repository query with a lock or a unique index (`…ForUpdate`, `(merchant_id, idempotency_key)`) suits a `@DataJpaTest` against real PostgreSQL.

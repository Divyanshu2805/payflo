# Project Status

[← Back to docs index](README.md)

_Last updated: 2025-11-24._

**Phase 1 of 2 — monolith.** The whole system is being built as a single Spring Boot application first;
the microservices split is a deliberate later phase. See
[Build strategy](architecture.md#build-strategy-monolith-first) for why.

| Area | Status |
|---|---|
| Architecture | Monolith (phase 1) — single app, single database |
| Domain entities | 15 of 15 built — all entities implemented, persistence layer only |
| Domain enums | Complete for the merchant, payment, vault, and operations domains |
| Repositories | Started — `merchant` (`AppUserRepository`, `MerchantRepository`, `ApiKeyRepository`), `payment` (`OrderRepository`, `PaymentRepository`, `PaymentTransitionLogRepository`), and `vault` (`VaultCardRepository`, `CardTokenRepository`) domains |
| Services / business logic | Started — `merchant` (`AuthService`, `ApiKeyService`), `payment` (`OrderService`, `PaymentService`), and `vault` (`VaultService`) domains |
| REST APIs | 13 endpoints — `POST /v1/auth/signup`/`POST /v1/auth/login`; `POST`/`GET`/`DELETE`/`POST .../rotate` under `/v1/merchants/{merchantId}/api-keys`; `POST`/`GET .../{orderId}`/`POST .../{orderId}/cancel`/`GET .../{orderId}/payments` under `/v1/orders`; `POST /v1/payments`/`POST .../{paymentId}/capture`; `POST /v1/vault/tokenize` (see [APIs](api.md)) |
| Auth (API key, JWT), rate limiting | `POST /v1/auth/signup`/`POST /v1/auth/login` are fully functional — signup hashes the password (bcrypt), login authenticates against the real `AppUser` row and returns a JWT, and bad credentials (wrong password or unknown email, indistinguishable) return a clean `401`. `WebSecurityConfig.jwtChain` now *requires* authentication for `/v1/merchants/**`/`/v1/admin/**`/`/actuator/**` — but no filter validates an incoming token, so those routes currently reject every request, including one with a valid token (see [Known gaps](gaps.md)). `/v1/orders`/`/v1/payments`/`/v1/vault` remain open. API key secret still stored unhashed. |
| Card tokenization/vaulting | `POST /v1/vault/tokenize` implemented — PAN encrypted with a per-card AES-256-GCM data key, which is itself wrapped with a master key (`vault.encryption.master-key`); only a token, brand, last 4 digits, and expiry are ever returned. CVV is validated but never persisted. A token is now consumable — `CardPaymentAdapter` decrypts and charges the vaulted card via `POST /v1/payments`. |
| Webhooks | Entities built — delivery, retry, and DLQ logic not started |
| Analytics | Not started — no dedicated entity in the design |
| Database migrations | None — schema is auto-generated by Hibernate (`ddl-auto: update`) |
| Tests | Only the generated `contextLoads` smoke test |

**Next up:** a `JwtAuthenticationFilter` so `/v1/merchants/**` is actually reachable again (it's
currently locked out for everyone, valid token or not — see [Known
gaps](gaps.md)), hashing the API key secret, and the rest of the
payment lifecycle (list orders, refund).

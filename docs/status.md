# Project Status

[← Back to docs index](README.md)

_Last updated: 2025-12-16._

**Phase 1 of 2 — monolith.** The whole system is being built as a single Spring Boot application first;
the microservices split is a deliberate later phase. See
[Build strategy](architecture.md#build-strategy-monolith-first) for why.

| Area | Status |
|---|---|
| Architecture | Monolith (phase 1) — single app, single database |
| Domain entities | 17 built — all 15 originally planned entities, plus `RefreshToken` (added 2025-12-08) and `OutboxEvent` (added 2025-12-16), neither in the original v1 design |
| Domain enums | Complete for the merchant, payment, vault, and operations domains |
| Repositories | Started — `merchant` (`AppUserRepository`, `RefreshTokenRepository`, `MerchantRepository`, `ApiKeyRepository`, `CustomerRepository`, `WebhookConfigRepository`), `payment` (`OrderRepository`, `PaymentRepository`, `PaymentTransitionLogRepository`, `OutboxEventRepository`), `vault` (`VaultCardRepository`, `CardTokenRepository`), and `operations` (`WebhookEventRepository`, `DlqEventRepository`) domains |
| Services / business logic | Started — `merchant` (`AuthService`, `RefreshTokenService`, `ApiKeyService`, `CustomerService`, `WebhookConfigService`), `payment` (`OrderService`, `PaymentService`, outbox publishing), `vault` (`VaultService`), and `operations` (Kafka-consumer webhook delivery pipeline — no classic service/controller layer, see [Practices](practices.md)) domains |
| REST APIs | 20 endpoints — `POST /v1/auth/signup`/`POST /v1/auth/login`/`POST /v1/auth/refresh`/`POST /v1/auth/logout`; `POST`/`GET`/`DELETE`/`POST .../rotate` under `/v1/merchants/api-keys`; `POST`/`GET .../{orderId}`/`POST .../{orderId}/cancel`/`GET .../{orderId}/payments` under `/v1/orders`; `POST /v1/payments`/`POST .../{paymentId}/capture`; `POST /v1/vault/tokenize`; `POST`/`GET`/`GET .../{id}`/`PUT .../{id}`/`DELETE .../{id}` under `/v1/merchants/webhooks` (see [APIs](api.md)) |
| Auth (API key, JWT), rate limiting | Both mechanisms are real and enforced, on two separate `SecurityFilterChain`s. JWT: `POST /v1/auth/signup`/`POST /v1/auth/login` are fully functional (bcrypt password, real `AppUser` check, clean `401` on bad credentials); login now also issues a DB-backed, hashed, rotating refresh token (`POST /v1/auth/refresh` exchanges it for a new access+refresh pair, single-use; `POST /v1/auth/logout` revokes one); `JwtAuthenticationFilter` validates the access token on `/v1/auth/**`/`/v1/merchants/**`/`/v1/admin/**`/`/actuator/**` (all but signup/login/refresh/logout) and resolves `MerchantContext`. API key: `ApiKeyAuthenticationFilter` validates an `Authorization: Basic base64(keyId:secret)` header (bcrypt-compared, grace-period-aware) on `/v1/orders/**`/`/v1/payments/**`/`/v1/vault/**`, resolving the same `MerchantContext` a different way. No per-resource authorization beyond "belongs to the caller's merchant" — no roles/permissions within a merchant (see [Known gaps](gaps.md) item 14). |
| Redis (rate limiting) | Redis added as a second datastore (`spring-boot-starter-data-redis`, `REDIS_HOST`/`REDIS_PORT`/`REDIS_PASSWORD` in `application.yaml`). Four interchangeable `RateLimiter` implementations in `common/rateLimit` — fixed window, sliding window (sorted set), sliding window (atomic Lua), token bucket (atomic Lua) — one active at a time via `app.rate-limit.method`. `ApiKeyAuthenticationFilter` enforces a per-API-key limit (`app.rate-limit.use-case.api-key.requests-per-minute`, `200` set in `application.yaml`) and answers over-limit calls with `429` (`RATE_LIMIT_EXCEEDED`, `Retry-After`/`X-RateLimit-*` headers). JWT-authenticated routes are not rate limited. See [Known gaps](gaps.md) item 20. |
| Idempotency | `IdempotencyFilter` (`common/idempotency`) guards `POST`/`PUT`/`PATCH` requests that send an `X-Idempotency-Key` header: the first request claims the key in Redis and runs; an identical retry gets the stored response replayed (`24h` TTL), and a retry while the first is still running is meant to get `409` (not yet actually mapped, see item 21). Only successful (`< 400`, non-empty) responses are stored, so a failed call can be retried cleanly. Requests without the header are untouched. Storage sits behind an `IdempotencyStore` interface (`RedisIdempotencyStore`). Not yet wired to a domain `idempotencyKey` column or a request-body fingerprint — see [Known gaps](gaps.md) item 21. |
| API key cache | `ApiKeyAuthenticationFilter` now looks keys up through an `ApiKeyCache` (`merchant/cache`, `RedisApiKeyCache`) before touching Postgres: a hit skips the `api_key` query; a miss loads the row, caches an `ApiKeyCacheEntry` (key id, both secret hashes, grace-period expiry, merchant id, environment, enabled flag) as JSON with a `5 minute` TTL, and continues. Cache read/write failures are swallowed and fall back to the database. The cache is never evicted on revoke or rotate — see [Known gaps](gaps.md) item 22. |
| Card tokenization/vaulting | `POST /v1/vault/tokenize` implemented — PAN encrypted with a per-card AES-256-GCM data key, which is itself wrapped with a master key (`vault.master-key`, in `common/config/AesEncryptionConfig` since 2025-12-16 — shared with webhook-secret encryption); only a token, brand, last 4 digits, and expiry are ever returned. CVV is validated but never persisted. A token is now consumable — `CardPaymentAdapter` decrypts and charges the vaulted card via `POST /v1/payments`. |
| Kafka (domain events) | `spring-boot-starter-kafka` added, with a local single-node broker in `services.docker-compose.yaml`. Order/payment writes go through a transactional outbox (`OutboxEvent`, `OutboxEventPublisher`) rather than calling Kafka inline — `OutboxPoller` (`@Scheduled`, 5s) picks up `PENDING` rows and publishes them to a per-aggregate-type topic (`app.kafka.topics`). `OrderServiceImpl`/`PaymentServiceImpl` publish `ORDER_CREATED`/`ORDER_CANCELLED`/`PAYMENT_CREATED`/`PAYMENT_STATUS_CHANGED`. Only `PAYMENT`/`ORDER` topics are actually produced to today; `REFUND`/`SETTLEMENT` are wired but unused. |
| Customers | `merchant/service/CustomerService.findOrCreate` — `POST /v1/orders` can now attach an optional `customer` (name/email/phone), looked up or created by merchant+email. No customer CRUD endpoints of its own yet. |
| Webhooks | Config CRUD implemented (`POST`/`GET`/`GET /{id}`/`PUT /{id}`/`DELETE /{id}` under `/v1/merchants/webhooks`) — per-merchant target URL, a server-generated secret (returned once, encrypted at rest), and an optional comma-separated event-type subscription filter. Delivery pipeline implemented: a Kafka consumer turns a domain event into a signed `WebhookEvent` row per subscribed target, a Redis sorted-set retry queue drives delivery attempts on a fixed backoff (1m→24h over 7 tries) via virtual threads, and exhausted events land in a DLQ table. Three bugs found while documenting this (see [Known gaps](gaps.md) items 23–25) were fixed the same day. |
| Analytics | Not started — no dedicated entity in the design |
| Database migrations | None — schema is auto-generated by Hibernate (`ddl-auto: update`) |
| Tests | Only the generated `contextLoads` smoke test |

**Next up:** role/permission checks within a merchant (right now any authenticated user or API key
can do anything that merchant can), recording `ApiKey.lastUsedAt` on successful auth, and the rest
of the payment lifecycle (list orders, refund).
